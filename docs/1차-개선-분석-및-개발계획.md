## 2. 기능별 현재 구현 상태 [사실]

### 2.1 로그인·인증: **없음**

- `src/` 전체에 login, signin, session, auth 관련 코드가 없습니다. `package.json`에도 인증 라이브러리가 없습니다.
- `src/trpc/init.ts`의 `createTRPCContext`는 빈 객체 `{}`를 반환합니다. 모든 프로시저가 인증 없는 `baseProcedure`입니다.
- `src/middleware.ts`와 `src/proxy.ts`가 없어서 라우트 보호도 없습니다.
- 결과적으로 **그룹 URL(`/groups/{id}`)을 아는 사람은 누구나** 조회, 수정, 삭제 요청을 할 수 있습니다.

### 2.2 현재 사용자 식별: 브라우저 localStorage

| 위치 | 내용 |
|---|---|
| `src/lib/hooks.ts` `useActiveUser()` | `localStorage['{groupId}-activeUser']`를 읽음 |
| `src/app/groups/[groupId]/expenses/active-user-modal.tsx` `ActiveUserModal` | 그룹 첫 방문 시 "당신은 누구인가요?" 모달을 띄움 → localStorage에 저장 |
| `src/components/group-form.tsx` (103~142행) | 설정 화면의 "로컬 설정 > 활성 사용자" 드롭다운 (서영 피드백 화면). 그룹 생성 시 **이름 일치(`p.name === activeUser`)로 참가자 id를 찾음** |

서버 프로시저(`expenses/create|update|delete`, `groups/update|delete|restore`)는 `participantId`를 **클라이언트 입력으로 그대로 받습니다**. 이 값은 활동 기록에만 쓰이고 검증되지 않습니다.

### 2.3 그룹·참여자 관리

- 생성: `src/lib/api.ts` `createGroup()`. 참여자는 **이름 문자열만으로** 생성되고, 계정 연결은 없습니다.
- 목록: `src/app/groups/recent-groups-helpers.ts`
  - `recentGroups`, `starredGroups`, `archivedGroups`를 localStorage에 저장합니다.
  - 서버의 `groups.list`(`list.procedure.ts`)는 클라이언트가 보낸 `groupIds`를 그대로 조회합니다.
- 참여: 그룹 URL 공유(`share-button.tsx`, `share-url-button.tsx`, QR) 또는 "URL로 불러오기"(`add-group-by-url-button.tsx`)로 합니다.
- 참여자 편집: `updateGroup()`(`api.ts`)에서 폼에 없는 참여자를 `deleteMany`하고 새 이름은 `createMany`합니다.
- 데이터 모델: `Participant`에는 `id`, `name`, `groupId`만 있습니다(`prisma/schema.prisma`).

### 2.4 지출 등록·수정

- 폼: `src/app/groups/[groupId]/expenses/expense-form.tsx` `ExpenseForm`
  - 기본 정보 카드: 지출 이름, 날짜, 지출 통화, 원래 금액, 환율, 카테고리, 금액, **"이건 비용 정산이에요"(`isReimbursement`, 933행)**, 결제한 사람, 메모, 반복 설정
  - 비용 부담자 카드: `paidFor`, 분할 방식 `splitMode`, 기본 분할 저장
  - 문서 카드: 영수증 첨부 (`ENABLE_EXPENSE_DOCUMENTS`가 켜졌을 때)
- 저장: `api.ts`의 `createExpense()`, `updateExpense()`. 참가자 id가 그룹 소속인지는 검증합니다.
- 금액은 최소 통화 단위 정수(`Expense.amount Int`)입니다. 분할은 `src/lib/shares.ts` `getExpenseShares()`가 정수 단위로 배분합니다.

### 2.5 일반 지출과 정산 기록의 구분

- `Expense.isReimbursement Boolean` 컬럼 **하나로만** 구분합니다. 정산도 같은 `Expense` 테이블의 한 행입니다.
- "지불 완료로 표시하기"(`src/app/groups/[groupId]/reimbursement-list.tsx`)의 동작:
  - 링크 주소는 `/groups/{id}/expenses/create?reimbursement=yes&from=..&to=..&amount=..`입니다.
  - 이 주소를 열면 `ExpenseForm`(199행 `isRepayment`, 252~280행)이 아래 값을 미리 채운 **일반 지출 추가 화면**을 엽니다.
    - 제목 "정산", 카테고리 1(Payment = "결제"), `paidBy=from`, `paidFor=[to]`, `isReimbursement=true`
  - 단비와 한결의 피드백이 가리킨 지점입니다.
- 계산에서의 처리:
  - `getBalances()`(`balances.ts`)는 **정산도 일반 지출처럼 포함**합니다. 그래서 송금 기록이 잔액을 상쇄합니다.
  - 통계(`src/lib/totals.ts`, `monthly-spending.ts`)는 `isReimbursement`를 **제외**합니다.
- 정산 상태(요청, 확인, 거절)를 저장하는 개념은 **없습니다**. 그룹에 접근한 누구나 다른 사람의 송금을 기록할 수 있습니다.

### 2.6 잔액·추천 정산 계산

- `src/lib/balances.ts`
  - `getBalances(expenses)`: 참가자별 `paid`(결제액), `paidFor`(부담액), `total = paid - paidFor`를 계산합니다.
  - `getSuggestedReimbursements(balances)`: 가장 큰 채권자와 채무자를 짝지어 송금 목록을 만드는 그리디 알고리즘입니다. 정렬 기준이 안정적이라 송금 하나를 처리해도 나머지 제안이 크게 바뀌지 않습니다.
  - `getPublicBalances(reimbursements)`: 송금 목록으로부터 잔액을 다시 구성합니다.
- `src/trpc/routers/groups/balances/list.procedure.ts`는 위 세 함수를 차례로 호출합니다. 화면에 나오는 잔액은 `publicBalances`입니다.
- 화면 구성:
  - `balances-list.tsx` `BalancesList`: 양수는 초록 막대(오른쪽), 음수는 빨간 막대(왼쪽)이고 **텍스트 라벨이 없습니다**.
  - 제목과 설명(`messages/ko.json` `Balances`): "잔액", "각 참가자가 지불했거나 받은 금액입니다." (단비, 한결 피드백 대상)

### 2.7 활동 내역

- `Activity` 모델: `activityType`, `participantId?`, `expenseId?`, `data?`
- `api.ts` `logActivity()`가 기록하는 유형은 6가지입니다: `UPDATE_GROUP`, `CREATE/UPDATE/DELETE_EXPENSE`, `SCHEDULE_GROUP_DELETION`, `RESTORE_GROUP`
- `participantId`는 클라이언트가 보낸 localStorage 값입니다. 값이 없으면 `activity-item.tsx`의 `useSummary()`가 "누군가"(`t('someone')`)로 표시합니다. 한결 피드백 대상입니다.

### 2.8 카테고리

- 카테고리는 마이그레이션 `20240108194443_add_categories`에서 0~42번이 SQL로 삽입됩니다.
- 한국어 라벨(`ko.json` `Categories`)에서 Dining Out은 "외식"입니다. **"식사"라는 라벨이 없어서 검색되지 않습니다.**
  - `category-selector.tsx`의 `CommandItem value`는 `"{id} {그룹명} {카테고리명}"` 형태라서, 이 문자열에 포함된 단어로만 검색됩니다.

### 2.9 인증이 필요한데 tRPC 밖에 있는 진입점

다음 진입점에도 인증과 권한 검사가 필요합니다.
- `src/app/groups/[groupId]/expenses/export/csv/route.ts`, `export/json/route.ts`: groupId만으로 전체 지출을 내보냅니다.

- `src/app/api/cron/purge-deleted-groups/route.ts`: `CRON_SECRET`으로 보호됩니다. 사용자 인증과는 무관하므로 유지합니다.

### 2.10 테스트·실행 환경

## 3. 요구 흐름과 현재 구현의 차이

요구 흐름: `로그인/회원가입 → 내 그룹 홈 → 그룹 만들기/보기 → 그룹 상세 → 지출/정산 → 송금 완료 요청 → 수령 확인 → 정산 완료`

| 단계 | 요구 | 현재 [사실] | 차이 |
|---|---|---|---|
| 첫 접속 | 로그인 화면 | `src/app/page.tsx` 소개 랜딩 + GitHub 버튼 | 로그인 화면 없음 |
| 인증 | 이메일·비밀번호, 세션, 서버 검증 | 없음 (`createTRPCContext` = `{}`) | 전부 신규 |
| 보호 URL | 비로그인 시 로그인으로 이동 | 모든 URL 공개 | 신규 |
| 내 그룹 홈 | 내가 **참여한** 그룹 (서버 기준) | 이 브라우저에서 **방문한** 그룹 (localStorage) | 데이터 출처가 다름 |
| 그룹 생성 | 생성자 계정을 구성원으로 연결 | 이름 목록으로 참여자 생성, 계정 연결 없음 | 신규 |
| 그룹 참여 | 초대 링크 + 계정 연결 + 중복 방지 | URL만 알면 접근, "나는 누구" 모달 | 신규 |
| 나는 누구 | 로그인 계정 = 참가자 | 기기별 localStorage 선택 | 대체 |
| 그룹 첫 화면 | 내 정산 현황 우선 | `/expenses`로 redirect, 지출 목록 | 신규 화면 |

| 활동 내역 | 실제 계정 이름 | localStorage 값 또는 "누군가" | 서버 세션 기반으로 변경 |

## 6. Prisma 스키마 및 인증 구조 변경 계획 [제안]

### 6.1 인증 방식

- **[제안] 인증 라이브러리: Better Auth**
  - 이메일·비밀번호 가입과 로그인을 기본 제공합니다. 비밀번호는 해시(scrypt)로 저장됩니다.
  - DB 세션(httpOnly 쿠키)을 쓰고 Prisma 어댑터가 있습니다.
- 대안은 Auth.js(NextAuth) Credentials입니다. 다만 Credentials 방식은 DB 세션을 지원하지 않고 JWT만 쓰는 제약이 있어서 차순위로 둡니다.
- Next.js 16, Prisma 7(`prisma-client` generator, `src/generated/prisma` 출력)과의 호환성은 설치 단계에서 **[확인 필요]**입니다. 호환되지 않으면 Auth.js로 전환합니다.
- 비밀키(`BETTER_AUTH_SECRET` 등)는 환경변수로만 관리하고, `src/lib/env.ts` zod 스키마에 추가합니다.

권한 판단 원칙:
- 모든 그룹 관련 프로시저와 라우트는 서버에서 `session.user.id`로 판단합니다.
  - 그룹 접근 조건: 그 사용자와 연결된 `Participant`가 그 그룹에 있어야 합니다.
- 클라이언트가 보내는 `participantId`나 localStorage 값은 **권한 판단에 쓰지 않습니다**.

### 6.3 정산과 잔액 계산의 연결 (기존 로직 보존이 핵심)

이 설계의 기본 원칙은 **확인된 송금만 잔액에 반영하고, 반영 방식은 기존 `isReimbursement` 지출 행을 그대로 쓰는 것**입니다.

1. 송금자가 요청하면 `Settlement(PENDING)`만 생성합니다. 잔액은 그대로입니다. 화면에는 "수령 확인 대기"로 표시합니다.
2. 수령자가 확인하면 같은 트랜잭션에서 두 가지를 처리합니다.
   - `Settlement`를 `CONFIRMED`로 바꿉니다.
   - `Expense(isReimbursement=true, paidBy=from, paidFor=[to], amount, categoryId=1)`를 생성하고 `expenseId`로 연결합니다.
3. 거절(REJECTED)이나 취소(CANCELED)는 잔액에 영향이 없습니다.

이렇게 하면 다음 코드를 **수정 없이** 그대로 쓸 수 있습니다.
- `getBalances`, `getSuggestedReimbursements`, `getPublicBalances`
- `totals.ts`와 `monthly-spending.ts`의 정산 제외 로직
- CSV/JSON 내보내기
- 기존에 체크박스로 만든 정산 행(레거시)

UI에서는 아래처럼 나눠 보여 줍니다.
- `isReimbursement=true` 행은 **지출 목록에서 숨기고**, 정산 관리의 "정산 완료 내역"에 표시합니다.
- 레거시 행은 "이전 방식 기록"으로 표기합니다.
- 정산 기록 지출의 수정 화면은 읽기 전용 안내로 바꿉니다. 직접 수정하면 정산 기록과 어긋나기 때문입니다.

"미정산" 상태는 저장하지 않습니다. 추천 송금 가운데 대기 중 요청이 없는 항목이 미정산입니다.

### 6.4 정산 규칙 (서버 검증)

| 규칙 | 처리 |
|---|---|
| 요청 권한 | 세션 사용자 = `fromParticipant.userId`만 요청 가능 |
| 확인·거절 권한 | 세션 사용자 = `toParticipant.userId`만 가능 |
| 취소 | 요청자만, `PENDING` 상태에서만 가능 |
| 중복 | 같은 (from, to) 쌍에 `PENDING`은 1건만 허용 (트랜잭션 안에서 검사) |
| 상태 전이 | `PENDING → CONFIRMED / REJECTED / CANCELED`만 허용. 종료 상태는 변경 불가 (요청과 확인을 같은 상태로 처리하지 않음) |
| 부분 송금 | 금액은 1 이상, 현재 추천 금액 이하. 확인 후 남은 금액은 다음 계산에서 다시 추천됨 |
| 지출 수정 후 금액 변동 | `PENDING` 요청 금액이 현재 추천 금액보다 크면 "금액이 바뀌었어요" 경고 표시. 수령자는 그대로 확인하거나 거절. 이미 확인된 기록은 사실 기록이므로 유지하고 잔액만 재계산 |
| 미연결 참가자 | 상대 참가자가 계정과 연결되지 않았으면 확인 불가. 요청은 "상대가 가입하면 확인할 수 있어요"로 대기 |
| 고지 문구 | "실제 은행 송금을 확인하지 않습니다. 두 사람의 확인 기록입니다." |

### 6.5 그룹 권한

- 그룹 생성자는 자동으로 `Participant(userId=생성자, role=OWNER)`가 됩니다.
- 참여자 삭제: 계정과 연결된 참가자, 또는 지출이 있는 참가자는 삭제를 막습니다.
  - 현재 `updateGroup`은 참여자를 `deleteMany`합니다. 이때 cascade로 지출이 지워지는지 **[확인 필요]**입니다. 스키마상 `paidBy onDelete: Cascade`라서 지출이 삭제될 수 있습니다.
- 그룹 삭제·복원과 초대 링크 재발급은 OWNER만 할 수 있습니다.
- 지출 등록·수정·삭제는 모든 멤버가 할 수 있습니다(기존 동작 유지). 활동 내역에 행위자가 남습니다.

## 8. 기존 기능 유지 및 데이터 마이그레이션 [제안]

1. **스키마는 추가형으로만 바꿉니다.** 새 테이블을 만들고 nullable 컬럼과 enum 값만 추가합니다. 기존 행을 지우거나 변환하지 않습니다. `isReimbursement`도 유지합니다.
2. **이름으로 자동 연결하지 않습니다.** 기존 `Participant.userId`는 전부 `null`로 시작합니다.
3. **기존 그룹을 계정에 연결하는 방법** (사용자가 직접 선택):
   - (a) "이 기기의 최근 그룹 가져오기"(`/groups/import`): 로그인 후 localStorage `recentGroups`를 읽어 목록을 보여 줍니다. 사용자가 그룹마다 "이 그룹에서 나는 ___"를 선택하면 연결됩니다.
   - (b) 예전 그룹 URL로 직접 접근: 연결된 계정이 없는 그룹(레거시)이면 같은 선택 화면을 보여 줍니다.
   - 처음 연결한 사람이 OWNER가 됩니다.
   - 그룹에 연결된 멤버가 1명 이상 생기면, 그 뒤로는 **초대 링크로만** 참여할 수 있습니다.
   - 보안 수준: 레거시 그룹은 원래 "URL = 접근 권한"이었습니다. 첫 연결까지는 같은 수준이고, 연결 이후에는 더 강해집니다. 이 점을 문서와 화면에 밝힙니다.
4. **잘못 연결된 경우**: OWNER가 참여자 관리에서 연결을 해제할 수 있고, 활동 내역에 남깁니다.
5. **기존 화면 URL 유지**: `/groups/{id}/balances`는 `/settlements`로 redirect합니다. `/expenses`, `/stats`, `/activity`, `/information`, `/edit` URL은 그대로 둡니다.
6. **유지하는 기능**: 다중 통화와 환율, 4가지 분할 방식, 반복 지출, 영수증 인식(OpenAI), 카테고리, CSV/JSON 내보내기, 그룹 삭제 유예와 복원, PWA, 다국어
7. **배포 전 백업**: 마이그레이션 전에 `postgres-data` 백업(`pg_dump`)을 받습니다. 실제 서버(203.234.62.166:3003) DB에 적용하는 절차는 서버 접근 권한이 필요하므로 **[확인 필요]**입니다.

| E2E 도우미 | 새 메뉴 구조(홈·지출·정산·통계 + 더 보기), "추가 옵션" 펼치기, 초대 참여(`joinGroup`), 글자로 표시되는 정산 결과("Receives $50.00") 반영 |

### 운영 안정성 보완 (검증 중 발견)
- **로그인 시도 제한:** better-auth의 가입·로그인 횟수 제한(비밀번호 대입 방지)은 운영에서 그대로 켜 둡니다. 테스트 스택만 `AUTH_RATE_LIMIT_DISABLED`로 끕니다.
- **비밀키 누락 시 즉시 실패:** 운영 서버에서 `BETTER_AUTH_SECRET`이 없으면 시작 단계에서 오류를 냅니다. `/api/health/readiness`도 503("BETTER_AUTH_SECRET must be set")을 반환하므로 Docker healthcheck가 잡아냅니다. 이미지 빌드는 `scripts/build.env`의 자리표시자로 진행되고, 이 파일은 이미지에서 삭제됩니다.
- **지출 저장 후 이동:** 지출을 저장하거나 삭제하면 원래처럼 **지출 목록**으로 돌아갑니다. 그룹 첫 화면은 그룹에 들어올 때 보여 줍니다.

### 확인하지 못한 것
- **Docker 이미지 빌드(`scripts/e2e.sh`):** Node 기본 이미지가 이 컴퓨터에 없어 내려받아야 하므로 실행하지 않았습니다. 같은 빌드 환경으로 `next build`가 성공하는 것은 확인했습니다.
- **운영 서버(203.234.62.166:3003)에 적용:** 아직 하지 않았습니다. 아래 체크리스트가 필요합니다.

### 운영 배포 체크리스트
1. 운영 DB를 백업합니다. 예: `docker exec spliit-feedback-db-1 pg_dump -U postgres postgres > backup.sql`
2. `container.env`에 `BETTER_AUTH_SECRET`(32자 이상, `openssl rand -base64 32`)을 추가합니다. `BASE_URL`은 지금처럼 실제 접속 주소로 둡니다.
3. 이미지를 다시 빌드하고 컨테이너를 다시 시작합니다. 시작할 때 마이그레이션 2개가 자동 적용되며, 둘 다 추가만 합니다.
4. 기존 피드백 그룹은 계정과 연결되지 않은 상태로 남습니다. 테스터가 로그인한 뒤 예전 그룹 링크를 열거나 "이 기기의 그룹 연결하기" 화면에서 본인을 고르면 연결됩니다. 처음 연결한 사람이 관리자가 됩니다.

## 1차 개발 완료 요약
- 사용자 흐름: **로그인/회원가입 → 내 그룹 홈 → 그룹 만들기·초대 참여 → 그룹 홈(내 정산 현황) → 지출 / 정산 → 송금 완료 요청 → 수령 확인 → 정산 완료**
- 피드백별 반영:
  - 단비: 지출과 정산 분리, 전용 송금 화면
  - 가은: 내 정산 현황을 맨 위에
  - 서영: 로그인 화면의 소개·사용법, 로컬 설정 제거
  - 한결: 계정, 정산 상태, 메뉴 정리, 활동 내역의 실제 이름
  - 민서: 필수 항목 중심 입력, 지출 목록과 정산 화면 정리
- 2차(AMI 연구실 맞춤: 공동 경비 입금·잔여금, 공용 물품·연구비 정산)는 구현하지 않았고, 다음 사용자 조사 후 진행합니다.
